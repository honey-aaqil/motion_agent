This is the first complete, consolidated specification. It supersedes the earlier prompts. It folds in six research reports (reasoning and repair, evaluation harness, call budget, multi-agent design, long-horizon reliability, safe self-improvement). Nothing is built yet. ## 0. How to use this document (builder: read this first)

You are a Flash-class model with limited context. Research shows that such models lose rules when many are loaded at once and drift over long sessions. So:

1. **Phase P-1 (first session) only:** split this document into the files named in section 15 (`SPEC.md`, `CONSTRAINTS.md`, `AGENTS.md`, `feature_list.json`, `HANDOFF_PACKET.md`) and set up the repo guards. After that, **never load this whole file again.** Each session loads only `CONSTRAINTS.md`, the delta part of `HANDOFF_PACKET.md`, the one `feature_list.json` entry you are working on, and the `SPEC.md` sections that entry names.
2. **One feature per session.** Stop at about 25 turns or 25,000 tokens, write the handoff, and start fresh.
3. **Verify, do not assume.** Anything marked **[verify]** comes from research reports, user notes or secondary sources. Check it against official documentation or a real test. If it is wrong, choose the closest alternative and record the change and reason in `DECISIONS.md`.
4. **Evidence is not authority.** Research numbers in this document are directional, mostly from other models and tasks. Where they conflict with your own measurements, your measurements win, and you write them in `SPIKES.md`.
5. **Never claim "done" in prose.** Only `scripts\verify_done.py` can mark a feature PASS (section 15).
6. **Ask the human only** for: missing keys or accounts, anything needing administrator rights (UAC), anything that deletes the user's files, new dependencies, schema changes, and the decisions listed in section 18.

## 1. Mission

Input per project: a two-column AV script (English master), Hindi and Tamil voiceover texts from the user, one audio file per scene per language from the user.

Output per project: for English, Hindi and Tamil, a finished 30 fps video in **9:16 (1080x1920)** and **16:9 (1920x1080)**, with the two ratios **composed separately**. That is 6 videos per project. Any length from seconds to hours. A video may take days to render; that is acceptable if the run is resumable and honest.

The user is **not a motion designer**. Every control is a menu, button or plain-language instruction. Primary style: explainer and educational. Secondary styles (kinetic typography, product promo, news or story) are added later by adding templates and presets, never new pipeline code.

## 3. Languages, audio and timing

- The **scene** is the unit of design, audio, rendering, editing and caching.
- Audio files: `S{nn}.{lang}.{wav|mp3|m4a}`, matched case-insensitively. Validate on upload; show missing or extra files.
- **Scene length = audio duration (ffprobe) + lead-in (default 0.3 s) + tail (default 0.5 s)**, pads set per channel preset. Each language gets its own timings from the same visuals.
- **Sentence-level sync only.** Cues attach to sentence anchors: `@scene.start`, `@s1.start`, `@s2.start+0.2s`, `@scene.end-0.5s`. Absolute timestamps in a cue are a validation error.
- **Finding sentence times:** split the VO text on `. ? ! … । ॥`. The VO text is the source of truth and is never rewritten beyond NFC normalization and one-time CRLF to LF. Run `whisper.cpp` (Windows `whisper-cli.exe`) on the scene audio with the right language flag and use **only its timestamps**. Largest model that fits RAM and time (test `small`, then `medium` for Hindi and Tamil). Match by order; if segment count differs from sentence count, combine `ffmpeg silencedetect` with character-proportional estimates. Store a confidence per anchor; low confidence is flagged in the editor. Single-sentence scenes need no alignment. Do not use Meta MMS aligner (non-commercial weights).
- Templates must tolerate 3 s to 120 s scenes: entrances at anchors, then a subtle looping hold motion. Scenes over 20 s need a visual change on every sentence.

## 5. Architecture

**One plain Python state machine over SQLite** (WAL mode, section 12). One process runs the loop; a light dashboard and editor server run beside it. Heavy work (Chromium, Whisper, rembg, ffmpeg encode) runs one at a time by default; P0 decides whether two parallel Chromium workers pay off (adopt only if peak stack memory stays within budget and speedup is at least 1.5x).

### 5.1 Principle: few LLM agents, many deterministic ones

Research found that debate, voting, peer review and unbatched role pipelines give no reliable gain over one model with a strong verifier at equal calls, and they break the call budget. So: **one model in isolated roles with separate contexts, coordinated by code, with most "agents" being deterministic tools.**

| # | Role | LLM or code | Input | Output (typed JSON) | Owner of | Calls | Build |
|---|---|---|---|---|---|---|---|
| 1 | AV Script Beat Parser | code | raw script | `VideoManifest` + `SceneBeat[]` | scenes rows | 0 | now |
| 2 | Art Director (StoryBible) | LLM, isolated | manifest summary (<=1,500 tokens) + template catalog IDs | `StoryBible` (palette tokens, type scale, pacing, motifs, entity glossary), <=400 tokens | story_bible | 1 per video | now |
| 3 | Asset Resolver | code | entities, motifs | `AssetMap` (local paths, hashes, fallback icons) | asset_map | 0 | now |
| 4 | Scene Author | LLM, isolated per scene | `SceneBeat` + StoryBible + `AssetMap` + `PrevSceneExitState` (<=80 tokens) | `SceneSpecDraft` | draft_spec | 1 per scene | now |
| 5 | Canonicalizer + Style Injector | code | draft + StoryBible | `CanonicalSceneSpec` (tokens resolved, defaults filled, clamps) | canonical_spec | 0 | now |
| 6 | Schema and Timing Validator | code | canonical spec | `ValidationReport` (codes, json paths, exact fix hints) | validation_log | 0 | now |
| 7 | DOM Geometry and Contrast Gate | code | spec rendered headless at 0%, 50%, 90% | `LayoutAuditReport` | audit log | 0 | now |
| 8 | Targeted Fixer / Fresh Restart | LLM, isolated | local: failing subtree + exact errors; global: original input + one-line verdict, **failed JSON withheld** | patched subtree or fresh draft | draft_spec (attempt 2) | 0.15-0.25 per scene | now |
| 9 | **Batched Visual Critic** | LLM (vision) | 4 rendered keyframes in a 2x2 montage with a 6x6 grid overlay | `VisualCriticReport` | vlm_review | about 0.25 per scene | **now, in shadow mode** |
| - | Debaters, peer reviewers, unbatched per-scene storyboarders | - | - | - | - | - | **never** |

**Role 9 rules:** runs after render on normal scenes (50% frame) and on scenes flagged by the DOM gate (10%, 50%, 90% frames). Writes only `scenes.vlm_review_json`; never edits a scene. **Shadow mode first:** it runs and logs but cannot block or trigger repairs until it passes calibration against both builders' labels (sensitivity and specificity at least 0.85 each; position-swap flip rate at most 5%; see section 13). When promoted, a critic-triggered repair counts as the scene's second call; if both calls are spent the scene goes to the human editor. Skipped or failed runs are logged `unjudged` and never block (fail open). Always the lowest-priority call in the queue; runs only when quota headroom exists. Disable if first-pass success is consistently above 88%.

### 5.2 State machine

```
VIDEO_NEW -> (parse, code) -> VIDEO_PARSED -> (Art Director, 1 call) -> BIBLE_LOCKED
 -> (Asset Resolver, code) -> SCENE_READY
SCENE_READY -> (Scene Author, attempt 1) -> DRAFT_AUTHORED
 -> (Canonicalizer) -> CANONICALIZED -> (Validator + DOM gate) -> VALIDATED | RETRY_ROUTING
RETRY_ROUTING: calls_used < 2 -> LOCAL_REPAIR or GLOBAL_RESTART -> DRAFT_AUTHORED
               calls_used == 2 -> NEEDS_HUMAN_EDIT (still renders a best-effort preview)
VALIDATED -> (render + canaries) -> SCENE_ACCEPTED   (extract ExitState for next scene)
```
- **Error routing:** `LOCAL` = at most 2 isolated element, timing, contrast or enum faults, or at most 1 isolated box fault. `GLOBAL` = 2 or more colliding boxes, over 20% overlap area, 3 or more distinct failing elements, unparseable output, or empty response.
- **Rate and fault handling never consumes an attempt:** HTTP 503, 429, timeouts and network errors roll the transaction back, release the scene lock, and back off. Only a received model response counts as a call.
- **Heartbeat leases:** `locked_until = now + 90 s` (monotonic clock for in-process timing). A crashed `IN_PROGRESS` scene returns to `SCENE_READY`. At startup, kill the old worker's process tree before reclaiming a lease.
- **Hard limits (in code, not prompts):** `MAX_LLM_CALLS_PER_SCENE = 2`; `MAX_BIBLE_CALLS_PER_VIDEO = 1` (+1 fallback, then a default StoryBible).

### 5.3 Typed messages, single owner per field

Agents never exchange free-form chat. They read and write typed JSON columns, one writer per column. `SceneBeat` is immutable after parse (no LLM may alter narration or duration). `StoryBible` is write-once per video; scenes reference tokens (`$bg_hex`, `$accent_hex`), never raw hex. `AssetMap` is immutable per scene; the author may only reference keys in it. `CanonicalSceneSpec` is regenerated deterministically from the draft and never edited by an LLM. `ValidationReport` carries only structured codes and numeric bounds (no raw stderr or HTML error text). Every attempt writes one immutable row to `scene_attempts` (prompt hash, raw response, canonical spec, validation and DOM metrics, latency, token counts including thinking tokens).

**Rejection rule for repairs:** reject any attempt-2 result that drops more than 1 entity from `SceneBeat.entities`, or removes narration coverage, to stop "passing" by deleting content. Track `narration_entity_coverage_ratio` and element-count delta between attempts.

### 5.4 Cross-scene consistency

One StoryBible per video, token injection in code, a one-hop `PrevSceneExitState` (<=80 tokens: previous template, persistent entities with normalized boxes, end transition). No growing chat history. Do not feed all previous scene specs to the author.

## 6. LLM gateway and call policy

**Facts:** the API returns HTTP 503 "high demand" often (3 of 5 test requests failed; 5 requests took about 198 s). A 503 means overload, not your quota; a 429 means quota. Treat both as normal.

**Gateway:**
- One persistent queue in SQLite. Requests are idempotent and cached by prompt hash. Editor requests outrank batch jobs. Never drop a request.
- **Rate governor:** minimum interval 15.5 s between requests (at most 3.87 per minute), measured with a monotonic clock. A table `api_rate_ledger` records every call. Before each call check the per-minute count and the daily count against `DAILY_QUOTA_CAP` (from `.env`, set after the P0 quota check).
- **Errors:** 503, 500, 502, 504, timeouts: exponential backoff with full jitter, `min(120, 2^retry + uniform(0,3))` seconds, no attempt consumed. After 5 consecutive 503s switch to the fallback model if configured, else pause the queue cleanly. 429 with a per-day signal: state `QUOTA_SLEEP_UNTIL_RESET` with a resume time [verify reset time in docs]; per-minute 429: wait about 62 s. 400 or a safety block: log it and route to repair; never retry identical input blindly.
- **Model config in one place** (SQLite or YAML): `MODEL_ID`, fallback list, temperature, `max_output_tokens`, thinking level. No hard-coded model strings anywhere in source. On every response, log and **assert `model_version` against the expected value** (catches silent auto-routing, which Google did on 2026-10-08 for older Flash models [verify]).
- **No catch-all fallbacks:** a retired model, a 404 or a parameter rejection must fail loudly, never return empty or default output.
- **Structured output:** use the API's JSON mode with a response schema [verify], and still validate every response yourself. **Generate the schema field descriptions and the system-prompt constraints from one Python source of truth**, so they can never contradict each other.
- **Thinking and tokens:** thinking effort counts against the output limit. Defaults: Scene Author `medium` (use `high` only when the scene has more than 8 elements), repair `low`, `max_output_tokens = 8192`. Log `thoughts_token_ratio` and `empty_or_truncated` for every call. If more than 5% of calls come back empty or truncated, or thinking exceeds 75% of tokens on rejected drafts, step the thinking level down one notch. P0 and the first experiment settle the final values.
- **Caching:** use free context caching for the static system prompt and schema where the API allows [verify].
- **Timeouts:** about 180 s per request. Slow is normal.
- **Logging:** every request writes model, task, status, latency, attempt and error code to `llm_log`, shown in the dashboard as "waiting for LLM (retry N, next try in M s)", clearly different from a failure.

**Per-scene call policy (the controller):**
1. **Call 1** Scene Author.
2. **Zero-call canonicalizer** immediately: clamp box overhangs under 5%, snap hex values to meet contrast, coerce enums and timing floats, prune unknown keys, bracket-repair malformed JSON. Then validate and run the DOM gate.
3. If it passes, done. Otherwise classify errors.
4. **Call 2** (only if calls_used < 2): `LOCAL` goes to Targeted Repair (failing subtree plus exact validator and pixel counterexamples; "change only the offending fields"). `GLOBAL` goes to a **verdict-only fresh restart** (fresh context, failed JSON withheld, one line naming the rejected failure class). Showing the model its own failed structure makes it copy it 33-68% of the time in the cited study [verify on our schema].
5. If call 2 fails: `NEEDS_HUMAN_EDIT`. **No third call by default.** An optional third call exists only when remaining daily quota is at least 3 times the remaining scene queue.
6. **Low-quota mode** (build later): when remaining daily quota is under 25 calls, the Scene Author takes 2 scenes per call. Behind a flag, evaluated on the golden set before use.
7. Measured repair-vs-restart rule: keep a repair route for an error category only if its measured recovery rate beats the fresh-restart rate for that category; otherwise route that category to fresh restart. Re-measure in the golden set.
8. Not allowed: unconditional best-of-N, Pro-model escalation as a design dependency (the stronger model may have no quota), LLM-vs-LLM debate.

**Daily quota arithmetic to keep in mind:** a 40-scene video needs roughly 48-50 calls. At 20 requests/day that is about 2.5 days per video, and a 60-scene golden-set run takes days. Paid access (or confirmed higher quota) changes the plan; P0 finds out which world you are in. If the quota is tiny, the improvement program and the vision critic wait, and only zero-call mechanisms run.

## 7. Quality gates

All gates run in **both ratios** at the start, middle and end of each animation cue, at every sentence anchor, and at scene end minus 0.1 s.

**Pre-render, zero model calls (roles 5-7):**
- Schema and enum validity; durations equal audio plus pads; cues reference existing anchors only.
- DOM box checks via headless render: overlaps that should not exist, outside safe margins or inside the caption-safe zone, text overflow or clipping, text below minimum size, contrast below 4.5:1 (3:1 for bold text of 56 px or more), missing or undecoded images, empty frames.
- Same frame rendered twice gives the same hash (determinism, this machine only).
- **Console and DOM trap:** any uncaught JS error, failed asset load, or visible "undefined"/"NaN" text in the page aborts the scene. Overflow check: `scrollWidth > clientWidth`. ffmpeg checks cannot see these.
- **A gate that crashes, times out or sees zero boxes is `GATE_EXEC_ERROR` and counts as FAIL, never PASS.**
- **Startup sabotage pre-flight:** the worker feeds one known-overlapping fixture and one low-contrast fixture (about 1.27:1) to the DOM gate and one malformed spec to the validator. If any does not return FAIL, abort startup before spending any API call.

**Post-render canaries (`scripts\render_canary_gate.py`), required before a scene or job becomes DONE:**

| ID | Check |
|---|---|
| INV-1 | `ffprobe`: both streams exist; video and audio duration differ by at most 0.05 s; video duration within 0.10 s of expected; frame count equals duration x fps (plus or minus 1) |
| INV-2 | `blackdetect=d=0.20:pic_th=0.90:pix_th=0.15` finds no unscheduled black interval (defaults of d=2 miss short glitches) |
| INV-3 | `freezedetect=n=-60dB:d=0.50` finds no static hold longer than the scene manifest allows (default 2.0 s dynamic, 0.5 s transitions) |
| INV-4 | `ebur128`, `silencedetect`, `volumedetect`: integrated loudness in [-24, -14] LUFS, true peak at most -1 dBTP, mean volume above -40 dB, no silence of 1.5 s or more outside scripted pauses |
| INV-5 | At startup and every 6 hours: render a fixed 3 s golden canary scene and compare `framemd5` to the stored golden. Mismatch halts before any API call (font, driver or browser drift) |
| INV-6 | SQLite ledger completeness: no gaps in scene index; every DONE row's file exists, is over 10 KB, and matches its stored SHA-256; zero expired leases |

Every canary has a **sabotage fixture** (a deliberately broken clip: 0.3 s black, 2.5 s frozen tail, audio at -45 dB, mismatched durations, truncated file) that must make the gate exit non-zero with a specific error code. Run `scripts\run_sabotage_suite.py` in CI and weekly.

**Vision (advisory):** judge each scraped asset (relevance 0-10, watermark or text overlay, blur or low resolution, crop suitability, recognizable real person, brand logo or trademark). Downscale to at most 1024 px. Role 9 is described in 5.1. If vision is unavailable for long, assets from sources with API license data may proceed marked `unjudged` and are re-judged later; scraped-source assets wait.

## 8. Visual system: templates first

1. A library of **12-15 tested templates**, each with separate **portrait** and **landscape** layouts: title slam, big statement, concept diagram, comparison split, process flow, timeline, stat counter, icon grid, chart, image focus with slow push, two-image contrast, quote, list reveal, outro. | | 9:16 | 16:9 |

| Side margins | 72 px | 96 px |
| Top margin | 150 px | 60 px |

## 9. Script format and parser

- Target: detailed two-column AV script (Markdown table, CSV/TSV, DOCX table) with `Scene/Time | VISUAL | AUDIO`. **Parse with deterministic code.** In AUDIO: `VO:` lines are narration; `MUSIC:` and `SFX:` go to cue lists. In VISUAL: quoted text or text after `TEXT:` is on-screen text; the rest is direction. Timecodes are hints only.
- Hindi and Tamil VO arrive as extra columns or separate files keyed by scene ID. A sentence-count difference between languages is information, not an error.
- **VO text is sacred:** NFC only; keep ZWJ/ZWNJ; no smart-quote conversion or spell-fixing; strip a leading BOM; CRLF to LF once at ingest. **Test:** VO text rebuilt from parsed JSON equals the LF-normalized NFC source byte for byte.
- Other layouts: detect and parse with the model; mark uncertain lines as questions answered by the user before approval 1. Never guess silently.
- `scenes/S01.json`: `{id, timecode_hint, directions[], onscreen_text[], vo{en,hi,ta}, music[], sfx[], style_hint, entities[], uncertain[]}`.

## 11. Editor and dashboard

**Editor** (`openfilm` Studio served locally; warn if the browser is not Chromium-based), in priority order:

2. Replace an asset (safe-license search or upload; uploads logged as user-supplied).
3. Regenerate one scene from plain language, sending only the scene spec JSON and slot contract. Preserve overrides by slot name. Show before and after stills; user accepts or rejects.

## 12. Rendering, resources, Windows hardening and monitoring

**Capture:** deterministic frame-by-frame. Seek to the frame time, wait for fonts and image decode, wait 2 animation frames, capture. Never screen-record. Follow `anidoodle`'s determinism contract.

**Chromium:** `chromium-headless-shell`, GPU disabled, software rendering, one worker by default, `--js-flags="--max-old-space-size=1536"`. **Kill and respawn the whole Chromium process tree after every scene or chunk** and verify with `psutil` that no stray `chrome` or `ffmpeg` process remains before the next one. Scenes over 30 s split into chunks of at most 900 frames; write each chunk and `state.json` before the next.

**Memory watchdog:** sum the private working set of the whole process tree. If it passes about 2.8 GB, or Windows reports under about 1.2 GB available, finish the frame, flush, respawn. Three respawns in a row: drop to 300-frame chunks, then flag. Free disk under 10 GB halts cleanly. Purge temp frames after each scene passes its canaries.

**CPU and priority:** while Chromium renders, limit ffmpeg and other work to 1-2 threads; run renders at below-normal priority. Whisper and rembg never run while Chromium renders.

**Encode:** H.264 (libx264), yuv420p, constant 30 fps, CRF 18-20, AAC 192 kbps 48 kHz, `+faststart`. Concatenate scene clips, then mix voiceover, optional music (ducked), optional SFX at cue times.

**SQLite (check `sqlite3.sqlite_version` at startup; require at least 3.51.3 [verify against SQLite release notes; a multi-connection WAL-reset corruption bug is reported fixed there]):**
`journal_mode=WAL; synchronous=FULL; busy_timeout=30000; wal_autocheckpoint=1000; journal_size_limit=67108864; foreign_keys=ON`. Short transactions (`BEGIN IMMEDIATE ... COMMIT`); never hold a read cursor during a render or an API call.

**Crash-safe file replace on NTFS:** write a temp file in the same directory, `fsync`, then `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)` with a retry loop of about 15 s for sharing violations (code in the kit). Use it for rendered clips, `status.html` and `HANDOFF_PACKET.md`.

**Windows hardening (scripts in the kit; the user runs the admin ones):**
- Power: no sleep, hibernate or disk timeout on AC; the main thread holds `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` for the whole run and clears it on exit (non-continuous calls are reported to fail on Windows 11 [verify]).
- Updates: set active hours, `NoAutoRebootWithLoggedOnUsers`, and **pause updates for the length of a long run** (policy keys may be ignored on Windows Home; check the edition).
- Defender: exclude **only the project folder** (`C:\motion-agent`). Do **not** exclude whole programs such as `python.exe`, `chrome.exe` or `ffmpeg.exe`.
- Time: keep W32Time running; use the monotonic clock for leases and the rate governor.
- Laptop: plugged in, performance power plan, lid close does nothing, optional CPU cap at 95% to avoid thermal shutdowns. Page file: a fixed 8-12 GB on the SSD (admin script).
- Auto-start and resume: a Windows Task Scheduler task at logon, restart on failure.

**Monitoring (zero LLM calls):** `scripts\watchdog_observer.py` runs every 5 minutes from Task Scheduler. It opens SQLite read-only (`?mode=ro`) and never changes state. It writes `status.html` (pipeline state, scenes done and ETA, last canary metrics, host vitals, last alert time) via the atomic replace. Alerts to the builders' phones through a push service (ntfy or similar), sent only for actionable conditions: expired lease plus 120 s, canary failure, 15 or more consecutive 503/429 (about 30 minutes) or an auth error, free disk under 10 GB, available RAM under 600 MB, WAL file over 128 MB. At most one alert per condition per 4 hours. **Dead-man switch:** on each healthy tick, push a message scheduled 15 minutes in the future that replaces the previous one, so silence means the phone gets an alert [verify the service's replace behavior with a real test]. The topic name is the password; put no sensitive content in messages. Cancel it when the job completes.

## 13. Evaluation harness (how "better" is measured)

Plain Python and SQLite, no platform.

**Datasets (separate files in Git, hashed):**
- `golden_release_v1.jsonl`: frozen, 60 scenes. 5 template families x 3 content-density tiers (low, medium, high), plus a tagged **hard subset of 25** (all high-density scenes plus boundary cases: long compound words, extreme-aspect assets, low-contrast palettes, tight anchors). **Start with a 30-scene seed set in P0** and grow to 60.
- `regression_bugs.jsonl`: append-only scenes from past validator or render bugs.
- `calibration_human.jsonl`: 100 stratified, double-labeled outputs (50 rejected, 50 accepted) for auditing local metrics and any vision judge.
- `error_analysis_pool.jsonl`: rolling 10-20 production failures, reviewed weekly, promoted to the next golden version quarterly.
- Never use past model outputs as gold.

**Metrics per run (table `scene_trials`):** first-pass validator success; final acceptance; calls per accepted scene (503 retries counted separately); repeated-failure rate (fails every repeat); flip rate between candidate and baseline; contrast and clutter scores from local computation on rendered frames; text-slot compression ratio; asset diversity (entropy); `narration_entity_coverage_ratio`.

**Protocol:** a **cached baseline** is run once per golden version and replayed from disk. A candidate runs the hard subset at temperature 0, one repeat (Stage 1, abort if first-pass success drops 12 points or more or schema failures exceed 1), then the full set at production temperature, **2 repeats per scene** (Stage 2). Compare by **paired per-scene differences**: exact mid-p McNemar for one repeat, paired percentile bootstrap (10,000 resamples) for two or more. If the variance of paired differences is high (above about 0.095), add a third repeat before declaring "no difference". Gate thresholds: SHIP at +10 points with a one-sided bootstrap lower bound above 0; BLOCK at -5 points, or a significant degradation, or persistent failures up by 2 scenes or more, or calls per accepted scene up by more than 0.25. At 60 scenes one repeat is underpowered; do not trust single-run comparisons. **Stage 3 (deterministic code only) is fully cached:** changing the canonicalizer, validator or DOM gate costs zero API calls to re-evaluate.

**Local visual metrics (zero calls):** WCAG contrast inside text boxes on rendered frames (hard fail under 4.5:1 where the JSON said it passed), spatial clutter (wavelet or subband entropy; flag the top 15%), bounding-box edge overlap. These come from slide-evaluation work and are an assumption for motion frames; validate against your own labels.

**Human contact sheet (5 minutes weekly):** an HTML sheet of blind side-by-side stills of discordant scenes (typically 10-18), plus 5 random concordant-pass scenes with the biggest drop in slot word count, plus 3 frozen "honeypot" scenes with known verdicts. BLOCK if human losses exceed wins by 4 or more, if 3 or more validator-passing scenes look broken or irrelevant, or if 2 or more of the 5 concordant scenes are hollow. If a honeypot verdict flips, you are drifting; fix the rubric before changing any prompt.

**Goodhart guards:** warn if mean words per text slot drops more than 20% from baseline, or the same 3-5 stock assets fill more than 30% of scenes.

**Vision-judge calibration (offline audit only; never a weekly gate until it passes):** both builders label 100 outputs Pass/Fail blind; require their agreement kappa of at least 0.70 first; the judge must reach sensitivity and specificity of at least 0.85 each (Youden's J at least 0.70), kappa at least 0.65, and a position-swap flip rate of at most 5%. Judge only composition and asset relevance, not things code already checks. Report any judge-based rate with a bias-corrected estimate and its interval.

## 14. Self-improvement program and model migration

**Headline finding:** automatic improvement loops run for more than one or two cycles mostly overfit or stall at this scale (60 scenes, 2 calls per scene, tiny quota). In a code-rendered explainer-video study, lessons did not compound and a closed-loop evolving playbook was misled by judge position bias into dropping facts. So improvement here is **gated, mostly deterministic, and human-approved.**

**Build in this order (start only after the pipeline works end to end and at least 2 videos are approved):**

1. **Deterministic rule and canonicalizer mining (0 API calls, about 10-15 minutes per cycle).** A script classifies each failure and editor diff into A (format or canonicalizable: fences, preambles, key aliases, type strings, box overflow fixable by clamping), B (template or exemplar missing: valid but poor layout), C (semantic drift: dropped facts). If A is at least 25% of failures, spend the first two cycles only on `canonicalizer.py` and new validator checks. **Every new rule needs a must-fail and a must-pass fixture and an ID that can be switched off or reverted in one step.** Replay all history offline to prove no regression.
2. **Append-only raw exemplar bank (0 search calls).** Store human-approved, post-edit scene specs. For a new scene retrieve 2-3 by template and layout metadata plus embedding similarity of the script text (small local embedding model if it fits RAM when Chromium is idle, otherwise BM25 and metadata match [verify]). No LLM-summarized memory, no mutation. **Compatibility gate:** an exemplar must pass 100% of the current validator and rules; retire exemplars that conflict with newer rules (re-validate on every rule change). Review the retired list monthly. Expect value from about 2-3 approved videos.
3. **Single-pass offline distillation (later, 1-3 analysis calls plus a held-out check, 15-20 minutes).** At about 10 or more approved videos and a daily quota of about 100 or more: a script computes exact failure statistics over the SQLite log; at most 3 bounded rule or prompt edits are proposed; each is tested on the holdout using the paired protocol. Never accept more than 3 changes per cycle.

**Not built:** online prompt search (GEPA, MIPROv2, TextGrad-style) at this evaluation size (selection noise of 8-13 points on 20-30 scenes; reported reversals on held-out data); closed-loop agent self-editing of prompts, templates or validators; LLM-summarized memory that rewrites itself.

**Never auto-modified by any improvement mechanism:** the validator and DOM gate logic, golden and immutable tests, `SPEC.md`, `CONSTRAINTS.md`, the license ledger rules, canary fixtures. Changes to these need the two humans.

**Cycle rules:** one optimization split and one frozen holdout; every proposed change goes through the Stage 1-2 protocol; changes are versioned (`rules_v12`, `exemplars_v7`, `prompt_v5`), logged in `DECISIONS.md`, and revert with one git revert or one `active=0` flag. Hold a weekly 30-minute review (section 15).

**Optional experiment, not a commitment (P14): DeepEvolve-style evolution.** DeepEvolve (Liu et al., arXiv 2510.06056, code at github.com/liugangcode/deepevolve [verify current state]) combines deep research with AlphaEvolve-style evolution: a plan, research, write and code loop with an evolutionary database as memory. It was shown on nine scientific-algorithm benchmarks, which is a different task from ours. Reasons it is not core: every generation costs many research and coding calls plus an evaluation, which our quota cannot support; the evaluator is our golden set, so it would be easy to overfit; and nothing public shows it working on layout or video. **Use it only if** daily quota is at least about 1,000 requests, the improvement steps above are done, and an offline sandbox branch exists. Scope it to evolving template parameters or canonicalizer rules with the frozen harness as the only scorer, an archive of variants with scores, no edits to protected files, a human approving the final merge, and a stop rule after a fixed number of generations without a held-out gain. Borrow the archive idea (store every variant with its score and parent) even if you never run the full system.

**Model migration checklist** (run whenever a model is deprecated or a silent update is detected; about 50-130 calls):
1. Model config lives in one place; assert the returned `model_version`.
2. Fail loudly on 404, 400, 503 and schema failures; no silent defaults.
3. Smoke test on 5 diverse scenes (10 calls): parameters accepted, output length versus `max_output_tokens`, no reasoning preamble before the JSON.
4. Patch the canonicalizer before touching prompts (fences, key casing, preambles), then re-score offline.
5. 20-scene stratified micro-canary on old and new models, paired against stored baseline outputs (24-40 calls).
6. If within 3 points of baseline after canonicalizer fixes, re-baseline the remaining scenes in background batches (48-80 calls). Change prompt text only if the same semantic error recurs at least 3 times.
Keep prompts modular: zero-shot, exemplars and an explicit output contract age best across model versions; fancy reasoning prompts age unpredictably.

## 15. Builder governance (full contents in the kit)

The builder (Antigravity + Gemini 3.8 Flash) is the weakest link, so mechanical guards enforce what prompts cannot:
- **`CONSTRAINTS.md`:** at most 5 hard rules, pasted verbatim at the start of every session and after any context reset.
- **`AGENTS.md`:** the session protocol (init, test-first, implementation, definition of done).
- **`feature_list.json`:** every feature starts `FAIL`. Only `verify_done.py` may flip it to `PASS`.
- **`tests/immutable/`:** held-out cross-feature and bad-input tests written by the humans (with help from the reviewer tools), locked read-only with `icacls`. The builder never edits them. Test the lock by trying to edit a locked file from the builder's terminal.
- **Git pre-commit hook:** blocks the commit unless 100% of earlier tests pass (read from a machine-written report, never from the agent's words), protected files are unchanged, the diff is at most 5 files and 250 net lines, and the static wiring check passes (every new public function is imported and called by the real pipeline, and breaking its return value makes at least one test fail).
- **Stop-and-ask triggers:** more than 5 files, a new dependency, a SQLite schema change, a test that contradicts `SPEC.md`, or the same test failing after 3 edit-test cycles.
- **Session cap:** about 25 turns or 25,000 tokens, one feature, then `HANDOFF_PACKET.md` and a fresh session.
- **Review:** each phase ends with a fresh-session review in a different model (Claude web or Gemini Pro chat) that receives only the handoff packet (invariants, the artifact slice, the test log, the reviewer instructions), never the generation chat. The builder never serves as final reviewer of its own work. A reviewer's claims are checked by tests, not trusted.
- **Weekly 30 minutes (two builders):** minutes 0-10 inspect `status.html`, the contact sheet, 3 frames and 3 audio snippets from finished renders; minutes 10-20 run a delta-scoped cross-model review of the week's diff plus `CONSTRAINTS.md`; minutes 20-30 write 1-2 new held-out tests, lock them, and run the sabotage suite.
